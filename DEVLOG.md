## 2026-07-11 — `ae9561f` — `/verify-email` and `/resend-verification`

## 2026-07-11 — `1b5083e` — `/login`, `/refresh`, `/logout` — real JWTs
- Added `POST /login` (`login.go`): verifies the password against the stored argon2id hash — always running the comparison, using a precomputed dummy hash when the email doesn't match anything, so a wrong-email and a wrong-password attempt take the same code path and roughly the same time (timing-attack mitigation) — rejects non-`active` accounts, then issues a token pair.
- Access tokens: `github.com/golang-jwt/jwt/v5`, **HS256**, signed with `JWT_SECRET` (required env var, no default — auth-svc now fails fast at startup if it's unset), 15-minute TTL, claims are just `user_id`/`email` plus standard `iat`/`exp` (no `iss`/`sub`/`aud`).
- Refresh tokens are *not* JWTs: 32 random bytes, base64url-encoded, stored in Redis as `refresh:<token>` → `userID` with a 7-day TTL. `POST /refresh` atomically pops the token (`GetDel`, so it's single-use), re-checks the user is still `active`, and issues a fresh pair. `POST /logout` just deletes the given refresh token from Redis.
- Verified live in this session (as part of documenting it): the full `register → verify-email → login → refresh/logout` cycle works end-to-end against real Postgres/Redis/mailpit containers.

## 2026-08-09 — *(uncommitted)* — Automatic failover: Patroni + etcd + HAProxy

> Note: this devlog is several commits behind the git log (the last recorded entry is `bf2f43a`; `main` has since moved through the ledger, Stripe deposits, fraud, reconciliation, frontend and streaming-replication work). This entry is recorded out of sequence rather than not at all.

- **The gap this closes**: streaming replication removed the risk of losing data, but not the outage. A dead primary meant the whole system was down until someone manually promoted a replica. That is not HA.
- **Topology replaced, not extended**: the `postgres` / `postgres-replica-sync` / `postgres-replica-async` trio is gone, along with `infra/postgres/primary-init.sh` and `replica-entrypoint.sh` (Patroni does both jobs — it creates the replication role and pg_hba entry from `patroni.yml`, and clones standbys itself). In their place: `etcd` + three *identical* `pg-node1/2/3` running Postgres 16 and Patroni in one container (`infra/patroni/Dockerfile` — one container because Patroni calls `pg_ctl`/`initdb`/`pg_basebackup`/`pg_rewind` directly and must share a filesystem namespace with `$PGDATA`). Node names carry no role: who leads, who is the synchronous standby and who is asynchronous is Patroni's decision, held in etcd, and it changes at runtime.
- **DCS is the whole point**: without consensus, a node that loses contact with the leader cannot distinguish "the leader died" from "I am the one partitioned", and promoting on that guess produces two nodes accepting writes — two ledger histories that each balance internally. Single-node etcd is documented in both `docker-compose.yml` and the README as a dev-only shortcut that reintroduces a single point of failure one layer down; prod needs 3–5 nodes.
- **`synchronous_mode: true` + `synchronous_node_count: 1`** reproduces the previous sync/async split and is what makes promotion safe: Patroni refuses to promote a node absent from the `/sync` key, and the leader cannot acknowledge a commit until a sync standby has flushed it — so every acknowledged transaction is on the only node eligible to win. `synchronous_mode_strict` deliberately left off, with the availability/durability trade spelled out.
- **Entry point: HAProxy over `target_session_attrs=read-write`**, argued in the README. Decisive reason: `target_session_attrs` asks Postgres "are you writable", HAProxy asks Patroni "does the consensus layer consider you leader" — and a node can answer the first correctly while being demoted. Secondary: one address instead of a three-host list duplicated across six compose entries, the README's test invocations, `cmd/seed` and `cmd/devtopup`. Host ports are unchanged (5432/5433/5434), so no existing command in the repo needed editing.
- **New shared module `pkg/pgha`** (wired into all six services like `pkg/outbox`): failover-tuned pool construction, `WaitForWritable` (services now build the pool *before* migrations, so one that starts mid-failover waits rather than `log.Fatalf`s), `Retry` (which still surfaces a genuine migration error immediately), and `IsUnavailable`.
- **Two consumer-loop bugs fixed, one of them real**: `accounts-svc`'s `user.events` reader busy-spun on fetch errors with no backoff (its `notifications-svc` counterparts always had one). More seriously, `notifications-svc`'s `transfer.events` retry ladder — 5 attempts over ~7.5s, then dead letter topic — is shorter than a failover, so the first failover would have DLQ'd a burst of perfectly good transfer notifications as poison. Errors classified as `pgha.IsUnavailable` now retry on a separate 5-minute budget without spending poison attempts.
- **`infra/failover/failover_test.go`** — a new module (it shells out to `docker compose`, a capability no service module should have), behind an explicit `FAILOVER_TEST=1` opt-in rather than the repo's usual `DATABASE_URL` gate, because it kills a container. It drives real `ExecuteTransfer` gRPC traffic through `ledger-svc`'s own pool, `docker kill`s the leader, and asserts: every acknowledged transaction present with **both** entries on the new leader; `SUM(entries) = 0` globally *and* per `transaction_id`; the app containers' `StartedAt`/`RestartCount` unchanged (so "recovered" cannot secretly mean "Docker restarted it"); `transfers-svc /healthz` back to 200; and the old node rejoining as a replica with never more than one leader.
- **Measured**: three runs at **25.4s / 23.6s / 23.6s** of write outage. ~20s of that is the leader key's TTL expiring, which is Patroni's hard floor — it silently clamps any `ttl` below 20 and only says so in a log line, so the config now states 20 rather than the 15 originally written.
- **Three bugs the test caught, none of which would have surfaced otherwise**: (1) `pgha.IsUnavailable` checked context errors before connect errors, so pgx's own `ConnectTimeout` — a `*pgconn.ConnectError` whose chain ends in `context.DeadlineExceeded` — read as "the caller's deadline", making it non-retryable and crash-looping all six services against a cluster mid-election; (2) HAProxy resolves `server` hostnames once at startup and caches forever, so every backend went L4CON after the nodes were recreated with new IPs (fixed with `resolvers docker`); (3) the test's own verification queries fell over on the connection failures they were verifying, reporting data loss where none occurred.
- Verified: full repo test suite green against the new cluster through HAProxy (`ledger-svc`, `transfers-svc`, `fraud-svc`, `pkg/outbox`, `notifications-svc` integration tests all unchanged); three consecutive failover runs passed with all five app containers at `RestartCount=0`; outbox relay's last error log lands exactly at the recovery instant and stops, with no restart.

## 2026-08-09 — *(uncommitted)* — Distributed tracing: OpenTelemetry + Jaeger

- **The gap this closes**: a transfer crosses gateway → transfers-svc → fraud-svc → ledger-svc, and correlating those four services' logs meant lining up timestamps by hand and hoping no two requests overlapped. One trace id now spans the whole path, with every gRPC hop and every SQL statement nested underneath.
- **`pkg/tracing`** is the only place OTel is configured: TracerProvider, OTLP/gRPC exporter to Jaeger, W3C `traceparent` propagation, plus the repo's span-attribute vocabulary and a `Fail` helper. Each service calls `tracing.Init(ctx, "<its real name>")` — the name matters, since a Jaeger dependency graph where every node calls itself "app" is worse than none.
- **Nothing depends on Jaeger.** No service has a `depends_on` on it, and an `Init` failure is logged rather than fatal: a bank that won't start because its observability backend is down has traded a real outage for an imaginary one. Without Init, the OTel API's no-op provider makes every instrumentation hook a cheap non-recording span — which is also exactly what the test suite runs with, since tests build handlers directly rather than through `main()`.
- **Auto-instrumentation**: `otelhttp` (servers + the gateway's proxy transport), `otelgrpc` via `StatsHandler` (servers + clients), `otelpgx` wired inside `pkg/pgha.NewPool` — one place covering all seven pools, because instrumentation that must be remembered in seven places will be missing from one.
- **The gateway is where a trace can die, and the reason is subtler than "the proxy strips headers".** The gateway is the trace ROOT: an inbound browser request carries no `traceparent` at all, so a faithful header copy still forwards nothing. The header has to be *injected* from the server span the gateway just opened, which is what `proxy.Transport = tracing.Transport(nil)` does. Without it you get three disconnected traces per request, each individually plausible.
- **PII policy lives in `pkg/tracing/attributes.go`**, next to the attribute keys rather than in a document that would drift: no credentials, no emails, no card data, no Stripe `client_secret`, no account *numbers* — internal account UUIDs only. Audited: no secrets travel in URLs in this codebase (codes/passwords/tokens are all in JSON bodies), which matters because `otelhttp` records URLs unasked. `otelpgx`'s `WithIncludeQueryParameters` is deliberately off — it would attach bind arguments, and those include password hashes, emails and session tokens.
- **Amounts ARE recorded**, as a documented trade: a money-movement trace without the amount cannot answer the questions traces exist for. Stored as a bare integer, no currency, no account number alongside.
- **Errors vs. correct refusals**: `tracing.Fail` marks spans with a low-cardinality `neobank.error.type` so "show me every failed transfer" is a Jaeger filter. Fraud rejections and `insufficient_funds` are pointedly NOT marked as errors — the system worked; marking them would put every blocked transfer in the same bucket as genuine breakage, destroying the distinction someone hunting problems needs.
- **Sampling** is 100% locally with `ParentBased(AlwaysSample())`. `ParentBased` is not decoration: the sampling decision is made once at the root and propagates in the `traceparent` sampled flag, so any production ratio below 100% still yields whole traces instead of half-sampled useless ones.
- **Also fixed in passing**: `gateway/Dockerfile` was on `golang:1.23-alpine` while its `go.mod` requires 1.25 — it built only because the toolchain silently downloads the newer one on every image build. Now 1.25 like every other service.
- **The bug the tests now guard**: `resource.Merge` refuses to merge resources with differing schema URLs and returns an error rather than picking one. `pkg/tracing` used `semconv/v1.26.0` while the SDK's `resource.Default()` uses `v1.43.0`, so all seven services logged one line — `tracing disabled: conflicting Schema URL` — and ran perfectly while emitting nothing. Jaeger listed exactly one service: itself. Nothing was visible from outside; the only symptom was an absence. `TestInit_SucceedsWithoutACollector` now asserts precisely that, and needs no collector because the exporter connects lazily.
- **Deliberately out of scope**: the async path. Kafka consumers and the outbox relay do not join a trace yet — trace context does not ride on the message, so their spans would root their own traces. That is next sprint's work (Kafka headers, and deciding whether producer→consumer is a child span or a span link).
- Verified end-to-end through the gateway, twice: a completed transfer produces one 55-span trace containing gateway, transfers-svc, accounts-svc, fraud-svc and ledger-svc with correct nesting — including the two INSERTs that are the double-entry pair — and a fraud-blocked transfer produces a 32-span trace that stops at fraud-svc with `ledger-svc` absent from the trace entirely, carrying `neobank.fraud.triggered_rule = amount_threshold`. A scripted scan of every span tag in both traces found no credential, token or email address.

## 2026-08-09 — *(uncommitted)* — Tracing the async path: outbox → Kafka → consumers, via span links

- **The gap this closes**: the trace died at the outbox write. Everything downstream — the relay publishing seconds later, notifications-svc sending the email, the WebSocket push, the reconciliation worker resolving a stuck transfer minutes on — produced spans that rooted their own traces and connected to nothing.
- **Why no Kafka library could fix it**: every off-the-shelf wrapper injects trace context into message headers *at publish time*, from a span live on the publishing goroutine. Here there is a table in between. The transaction commits, the HTTP span ends, the response goes back — and only then does a separate relay goroutine, which never heard of that request, read the row and publish it. There is nothing to inject from. The context has to cross the gap in the only thing that spans it: the row.
- **`trace_context JSONB`** on all three outbox tables plus `transfers` and `deposits`. `outbox.InsertEvent` serializes the propagator's carrier into it **inside the same transaction as the event**, so the context is exactly as durable as the event it describes. JSONB rather than TEXT so `SELECT trace_context->>'traceparent' FROM outbox WHERE published_at IS NULL` works from psql with no code. Nullable by contract: rows predating the column, and rows written with tracing off, legitimately have none — absent context is a state, never an error.
- **Span links, not parenting — the decision this sprint turns on.** Parenting the publish to the originating request is entirely possible (the context is right there) and wrong. A parent's duration is defined to contain its children's; the request took 50ms and the publish happens a second later — minutes later after a Kafka outage — so Jaeger would draw a 50ms bar with a child starting well after it ended, and every duration aggregate over the request span would be corrupted. `tracing.StartLinkedRoot` uses `WithNewRoot` + `WithLinks` to say what is actually true: separate work, causally related, navigable from both ends.
- **Kafka headers carry the DELIVERY trace, not the original request's.** Consumers therefore nest as ordinary children of the publish — correct, because they genuinely are caused by it and follow closely — while the link keeps the route back to the request one click away. One transfer produces two traces: the synchronous request, and the delivery trace linked to it.
- **Consumers instrumented**: notifications-svc (all three readers), gateway (both, incl. the WebSocket push), accounts-svc (UserActivated). Retries and the DLQ are spans of their own, so a message that was retried three times and dead-lettered reads as exactly that: three `attempt` siblings with rising `neobank.retry.attempt`, then a `dlq publish` marked as an error — because reaching the DLQ *is* a delivery failure, unlike a fraud rejection.
- **Reconciliation is the showpiece.** Those workers wake on a timer and have no parent by construction. With the origin trace stored on the row, the worker's span links back to the request that created it — so a stuck transfer's whole story is navigable: the original request, where it stopped short of a terminal state, and the separate trace minutes later that finished it. `RECONCILE_STALE_AFTER` is now overridable from `.env` purely so this is demonstrable without a two-minute wait per attempt.
- **The bug the package's own tests caught**: `InsertEvent` now requires the `trace_context` column, and `pkg/outbox`'s test helper still created the old table shape. The insert failed inside an open transaction, `t.Fatalf` ran `pool.Close` from cleanup, and the whole package hung for 90 seconds on a WaitGroup instead of reporting a failure. Fixed in the test helper *and* in the package doc comment, which is the contract each service's migration is written against — the doc now states the column is required.
- Verified end-to-end against the live stack, both halves of the DoD: a completed transfer yields a 55-span synchronous trace plus a separate 17-span delivery trace whose `outbox publish TransferCompleted` root links back to it and which reaches notifications-svc and the gateway's WS push; and a genuinely stuck transfer (created by stopping fraud-svc, so it returns 202 pending through the real degradation path rather than a hand-written row) is resolved 25.4s later by the worker, in a separate trace linking back to the original request, carrying `reconcile.trigger=stale_pending`, `stale_for_seconds=25.37`, `resolution=failed`.
- Deliberately out of scope: Prometheus/Grafana metrics.

**Dev infra** (`docker-compose.yml`): `postgres:16-alpine` (db `neobank`, 2 migrations so far: `users`, `verification_codes` — only consumed by auth-svc), `redis:7-alpine` (refresh tokens + resend-verification rate limiting, only consumed by auth-svc), `mailpit` (fake SMTP + web UI on `8025`, only consumed by auth-svc), `kafka` (KRaft single-node, not consumed by anything yet).

**Auth flow, end to end**: `POST /auth/register` (argon2id-hashed password, 6-digit emailed code) → `POST /auth/verify-email` (activates the account) → `POST /auth/login` (returns a 15-minute HS256 JWT access token + a 7-day single-use Redis-backed refresh token) → `POST /auth/refresh` (rotates the pair) → `POST /auth/logout` (revokes the refresh token). Every route except the pre-auth ones above (plus `/`/`/healthz`) requires `Authorization: Bearer <access token>` at the gateway.

**Not yet built**: gRPC contracts in `proto/` (scaffolding only, no service uses it), the 5 non-auth services' actual business logic, `/auth/forgot-password` + `/auth/reset-password` on auth-svc (routes are reserved at the gateway already), rate limiting, service discovery, automated tests, and lint in CI.
